# 0122 — A pre-tokenizer that does not split

**Issue:** [#122](https://github.com/CyrilB1531/data.net/issues/122) · **Umbrella:** [#105](https://github.com/CyrilB1531/data.net/issues/105) · **Date:** 2026-08-14

## Context

Two file shapes need a mode `BpeTokenizer` does not have, and they need the same one.

`TokenizerJsonLoader` **refuses** a bare `ByteLevel` whose `use_regex` is off, and **silently mis-loads** a
model that declares no `pre_tokenizer` at all — mapping it to the classic `Whitespace` split. The second is
worse: it produces wrong tokens without saying so.

`PreTokenizerPattern` is a `string?` where `null` already means `Whitespace`, so there is no state left to
mean "do not split". #143 recorded that gap deliberately rather than closing it, because the lot that needs
it should be the one that pays for it.

## What is measured

All against `tokenizers` 0.23.1, re-taken on 2026-08-14 after #143 and #145 changed this code.

### D1 — an absent `pre_tokenizer` is not `Whitespace`, and the difference is live

Vocabulary `{[UNK], a, b, ab}`, merge `(a, b)`, `fuse_unk` on:

| `pre_tokenizer` | `"aZ Za"` |
| --- | --- |
| absent | `['a', '[UNK]', 'a']` |
| `Whitespace` | `['a', '[UNK]', '[UNK]', 'a']` |

Without a pre-tokenizer the space is itself an uncovered character, so `Z`-space-`Z` is one run and
`fuse_unk` collapses all three. With one, the two `Z`s are in different pieces and cannot fuse.

**DataNet loads the second for a file declaring the first.** No refusal, no warning, different ids.

### D2 — `use_regex: false` hands the model one piece

`ByteLevel(add_prefix_space=false, use_regex=false)` over `"hello world"` gives `['helloĠworld']` — the
whole text, byte-mapped, unsplit. DataNet refuses this file by name today.

### D3 — with no split, `add_prefix_space` applies once

| `add_prefix_space` | pieces |
| --- | --- |
| `false` | `['helloĠworld']` |
| `true` | `['ĠhelloĠworld']` |

One space, at the front of the one piece — not one per word, because there are no words.

### D4 — "one piece" means one piece per added-token segment

Added tokens are carved out before any split runs (#104, ADR 0022). Measured with `<sep>` added and
`use_regex` off, `"a b<sep>a b"` gives `['aĠb', '<sep>', 'aĠb']`.

So the mode does not need a new stage: it is the existing per-segment structure with the split removed.
`BpeTokenizer.EncodeSegment` already calls the pre-tokenizer once per segment.

### D5 — a no-split encoding round-trips byte for byte

`use_regex: false` over `"hello world  again"`, `"  leading and trailing  "` and `"café 😀"` decodes back
to the input exactly, as it does with `use_regex` on. The round-trip guarantee byte-level BPE exists to
provide survives the mode — which is what makes it worth having rather than refusing.

## Design

### The three legal shapes, and the refusal that makes them legible

`PreTokenizerPattern`'s `null` currently means `Whitespace`, which is why "no split" cannot be said. The
fix is to stop overloading it, and the cost of that is a silent change: a caller building
`new BpeVocabulary(vocab, merges)` with no pattern gets `Whitespace` today and would get no split
afterwards, with nothing to tell them.

**So the ambiguous state is refused rather than reinterpreted.** `BpeTokenizer`'s constructor accepts:

| shape | means |
| --- | --- |
| `PreTokenizerPattern` set | split on it, after `PreSplit` if declared |
| `PreSplit` set, `PreTokenizerPattern` null | the pre-split is the only split (#143's shape 4) |
| `NoPreTokenizer = true`, both patterns null | **do not split**; the segment is one piece |
| everything else | `ArgumentException` naming what was and was not declared |

"Everything else" is two cases: nothing declared at all — the shape whose meaning changed — and
`NoPreTokenizer` set beside a pattern, which contradicts itself. A caller who meant the classic lineage
writes `PreTokenizerPattern = BpePatterns.Whitespace`, which is a new member holding the pattern the
constructor used to supply.

An explicit property rather than a sentinel string: a magic value inside a `string?` is the ambiguous
shape #143 rejected on measured grounds, and a pattern that happened to equal the sentinel would change
meaning.

### What each loader does

| where | today | after |
| --- | --- | --- |
| absent or null `pre_tokenizer` | `(null, null)` → `Whitespace` | `NoPreTokenizer = true` |
| `Whitespace` pre-tokenizer | `(null, null)` → `Whitespace` | `PreTokenizerPattern = BpePatterns.Whitespace` |
| bare `ByteLevel`, `use_regex: false` | refused by name | `NoPreTokenizer = true` |
| everything else | unchanged | unchanged |
| `BpeFilesLoader`, classic | `null` → `Whitespace` | `BpePatterns.Whitespace` |

The refusal `TokenizerJsonLoader` raises for `use_regex: false` goes away, and its reason with it — it
said `BpeTokenizer` "would split it on word boundaries and drop the whitespace between them", which was
true and stops being.

### `BpePreTokenizer`

Gains nothing but a third case: no pattern at all, so `Split` appends the text unchanged. The behaviour
rules from #145 — the four `SplitBehavior` values and `invert` — do not apply, because there are no
matches to arrange.

## Evidence

A corpus `bpe_no_split.json`, models carried in `metadata.models`, on the shape #118 through #145
established. Five models, each for something no other distinguishes:

1. **no `pre_tokenizer`**, and **`Whitespace`** beside it, over `"aZ Za"` with `fuse_unk` — D1's pair, and
   the only case that shows the live defect rather than the refused one;
2. **`ByteLevel` with `use_regex: false`**, and the same with it on — D2;
3. **`use_regex: false` with `add_prefix_space` on** — D3, the one space at the front;
4. **`use_regex: false` with an added token**, whose text spans it — D4, which proves the mode is
   per-segment rather than per-text.

Plus the round-trip of D5, asserted through `Decode` rather than recorded as tokens: what it proves is
that the input comes back, and a token list would only prove itself.

`add_prefix_space` is **not** off throughout this corpus, unlike #143's and #145's. It cannot be: D3 is
about what the prefix space does when there is no split, so the setting is the measurement. That does not
reopen #122's own prefix-space rule — the per-`Split`-piece placement — because with no split there is one
piece and the two rules agree by construction.

## Out of scope

**The `Sequence` prefix-space rule** — per added-token segment here, per `Split`-produced piece in
HuggingFace. It is the second half of this issue as filed, it needs a `Split` step to be observable, and
it does not interact with a mode that has no split at all. It stays with #122 as a follow-up rather than
being folded in, because bundling it would make this lot's corpus measure two rules at once — the mistake
ADR 0022 §10 records.

**`Split`'s `behavior` and `invert`** ([#145](https://github.com/CyrilB1531/data.net/issues/145), landed):
they arrange matches, and this mode has none.

## Risks

- **A caller building a `BpeVocabulary` by hand with no pattern now gets an exception.** That is the point
  — the alternative was the same caller silently getting a different token stream — but it breaks the
  shortest construction that works today. **Measured: 15 construction sites in the tree, 11 of which
  declare no pattern and would be refused**, including one inside `TokenizerJsonLoader` itself. They must
  be updated in the same commit as the refusal, and each one is a decision rather than a rename: whether
  that site meant `Whitespace` or meant "it does not matter here" is exactly what the current spelling
  hides.
- **`BpeVocabulary` takes a fourth change in one unreleased version**, after #104, #143 and #145. The
  package is `0.3.0` and unpublished.
- **The mode is reachable by two file shapes that are not otherwise alike** — an absent `pre_tokenizer`
  and a byte-level model with `use_regex` off. They agree on the split and differ on everything else
  (byte mapping, the prefix space), so the corpus carries both rather than assuming one stands for the
  other.
